\# PROJECT: ProxyPatient - Synthetic Patient Scenario Generation for Diabetes Risk Awareness

\## 1. IDEA (do not change)

ProxyPatient is a STRICTLY Generative AI health-awareness / research-exploration tool. It learns patterns from a real INDIAN health survey dataset and generates many SYNTHETIC patients under different "what-if" conditions. It then computes an outcome statistic on each generated cohort, validates statistical fidelity, and compares scenarios.

It is NOT a diagnosis, treatment or individual-prediction tool.

\## 2. PROJECT FLOW (8 steps, keep this order)

1\. Data source: Indian dataset (Section 3)

2\. Ingestion and preprocessing: handle missing values and DHS special codes, normalise numerics, encode categoricals (state via embedding or region grouping)

3\. Scenario generation: conditional generative model (CVAE) trained on the preprocessed data, generating a batch per what-if condition

4\. On-demand request: the user picks a baseline profile and what-if conditions

5\. Outcome computation: one outcome statistic per generated batch, computed from the batch, never from a single prediction

6\. Validation and fidelity: KS-test, correlation comparison, utility check with a classifier trained on real data

7\. Scenario display: labelled scenario cards, side-by-side comparison, methodology panel

8\. Outcomes and impact: health awareness, SDG 3, explicit "not a diagnosis" scope

Final output: per-scenario outcome statistics + a fidelity report.

\## 3. DATASET

\- PRIMARY: NFHS-5 India (2019-21), Government of India survey distributed by the DHS Program. Real data, about 724k women (15-49) and 102k men (15-54).

\- Files we provide (Stata format, kept LOCAL and PRIVATE in data/raw/):

\- IAIR7EDT (women's Individual Recode, main file)

\- IAMR7EDT (men's Recode)

\- IAPR7EDT (Household Member Recode, optional, only if some measurements are found there)

\- docs: DHS-VII Recode Manual, Recode Map, Biomarker questionnaire, NFHS-5 Final Report (FR375)

\- Variables to use (verify exact column names from the file's own metadata, never guess): age, sex, BMI/height/weight, waist and hip, blood pressure, random blood glucose, wealth index, education, urban/rural, state, tobacco, alcohol, survey weight.

\- OUTCOME: elevated random blood glucose (default rule: >= 200 mg/dL, set in a config file). This is a PROXY, not a clinical diagnosis, and it cannot separate type 1 from type 2. Label it "elevated glucose (proxy)" everywhere. Never call it "diabetes prevalence" or a person's "risk".

\- If no usable glucose variable exists in the files, STOP and report. Do not invent a substitute.

\- BACKUP (only if NFHS-5 fails): NMB-2017, Mendeley Data, DOI 10.17632/twp8xw6p25.1, CC0, 7,496 high-risk Indian adults. Label any result "among high-risk adults". Never merge it with NFHS-5.

\- FORBIDDEN: Diabetes 130-US Hospitals, Pima Indians, UCI Early Stage Diabetes (Bangladesh), any diabetes dataset of unclear origin. Our slide's step 1 mentions Diabetes 130-US; ignore that and use NFHS-5.

\- LICENCE RULES: never commit, upload or host raw NFHS-5 data (add data/, \*.dta, \*.sav, \*.zip to .gitignore first). The app may load only model weights, preprocessing objects and aggregate stats. Suppress any aggregate cell with fewer than 30 real respondents. Never display a real respondent row.

\## 4. MODEL AND BACKEND

\- Main model: Conditional VAE with a mixed-type decoder (Gaussian heads for continuous variables, softmax heads for categorical ones), a KL term with annealing, and a learned embedding for state.

\- Baselines for comparison: CTGAN and TVAE.

\- Conditioning variables (what-if inputs): sex, age band, urban/rural, wealth quintile, BMI band, hypertension, tobacco, alcohol. Do NOT offer glucose as a what-if, because it is the outcome.

\- Generated variables: age, BMI, waist, hip, blood pressure and random glucose, all sampled from the model.

\- Outcome statistic: percentage of the generated cohort with elevated glucose (proxy), with a bootstrap 95% CI and the difference from baseline in percentage points. Computed from the generated data, never hardcoded.

\- What-if means "how the synthetic cohort shifts when the population profile changes", not a causal intervention. Say so in the UI.

\- Synthetic patients must be newly generated by the model, never copied or jittered real rows.

\- Validation to implement: KS-test and Wasserstein per continuous column, correlation-matrix comparison, utility check (a classifier trained on real data confirms the outcome shifts in the expected direction), train-on-synthetic-test-on-real, real-vs-synthetic classifier test, conditional-fidelity check against real subgroups (warn when fewer than 30 real people), and a distance-to-closest-real-record privacy check.

\- Backend: Python + PyTorch, exposed through a simple FastAPI REST service (baseline profile, generate, compare, validation report). Plain request/response only.

\## 5. WHAT TO USE / WHAT NOT TO USE

USE: deep learning (MLP, VAE/CVAE), ML for validation (logistic regression / XGBoost), embeddings.

DO NOT USE: agents, multi-agent systems, tool-calling, autonomous workflows, chatbots, LangChain/LangGraph/AutoGen, or an LLM to generate rows. No CNN, RNN or tokenizers (tabular data, they don't fit). Scenario summary text is built from string templates filled with computed numbers.
